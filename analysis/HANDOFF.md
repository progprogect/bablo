# Передача задачи: аналитика журнала сделок

Документ для сессии, которая продолжит работу. Пишется как для того, кто видит
проект впервые: что хотели, что уже готово, обо что споткнулись и что делать дальше.

**Ветка:** `claude/dreamy-feynman-kixump`

---

## 1. Что хочет пользователь

Две задачи по закрытым сделкам из журнала:

1. **Найти зависимости.** Что общего у сделок, закрывшихся по стопу, и что — у
   закрывшихся по тейку. Какие индикаторы и данные на входе с этим связаны, а какие
   не влияют вообще.
2. **Контрфактический разбор.** Что изменило бы исход сделок, закрытых по стопу.
   Ограничения заданы пользователем явно: **тейк не ближе 1:1**, **стоп не шире 2 ATR**.
   Также интересует вход раньше/позже.

Отдельно спрашивал про TimesFM от Google. Ответ дан: не подходит — это модель
**прогнозирования** ряда, а для задачи 2 прогноз не нужен вовсе (реальные свечи после
закрытия сделки уже лежат в БД, и читать факт лучше, чем его предсказывать), для
задачи 1 это другой класс задачи (атрибуция признаков, а не прогноз), и главное —
узкое место в количестве сделок, а не в мощности модели. Если пользователь вернётся
к этому вопросу, см. раздел 7.

### Что уже проверено (не перепроверять заново)

- Поднимался локальный PostgreSQL 16, накатывались **все 22 настоящие миграции** из
  `server/drizzle` — выгрузка отработала на схеме, идентичной боевой, все 13 файлов
  на месте.
- **Гарантия read-only не декларативная.** Под `default_transaction_read_only=on`
  сервер отклонил `DELETE`, `UPDATE`, `DROP` и `INSERT`. Отклоняет сам PostgreSQL,
  поэтому опечатка в SQL физически не может ничего испортить.
- Загрузчик разбирает формат дат PostgreSQL (`2026-03-10 17:35:00+00`) и правильно
  восстанавливает геометрию входа.
- Отчёты не падают на выборке из двух сделок и честно отказываются считать.
- На синтетике с **заложенным** эффектом: при 600 сделках пайплайн находит именно
  его и ничего постороннего, при 120 — честно сообщает, что эффект неотличим от шума.

## 3. Обо что споткнулись: данных нет

**Пайплайн готов, данных нет.** Всё упирается в доступ к боевой БД на Railway.

### Ограничение этой сессии (важно понять причину)

Cloud-сессия Claude Code **не имеет raw-TCP наружу**. Проверено напрямую:

```
github.com:443  -> соединение установлено      (HTTPS через прокси)
1.1.1.1:53      -> timeout                     (DNS)
github.com:22   -> timeout                     (SSH)
```

Railway отдаёт Postgres на `*.proxy.rlwy.net` со **случайным высоким портом**, а не
на 443. Значит `psql` из cloud-сессии не подключится **никогда** — это не вопрос прав
и не чинится разрешением доменов в настройках окружения.

Дополнительно: хосты `backboard.railway.app` и `backboard.railway.com` (GraphQL API
Railway) отклонены сетевой политикой окружения — достать строку подключения через
API тоже нельзя.

### Что из этого следует для следующей сессии

- **Локальная сессия Claude Code (на машине пользователя) — сработает.** Там есть
  обычный доступ в сеть.
- **Другая cloud-сессия — упрётся в то же самое.** Если следующая сессия тоже
  облачная, подключаться к БД бессмысленно: нужен один из обходных путей раздела 5.

## 4. Про правило проекта и разрешение пользователя

`CLAUDE.md` запрещает трогать боевой контур вообще, **включая read-only SELECT**.
Пользователь это правило **явно переопределил** — дважды: сначала дал токен Railway и
попросил скачать данные, затем написал «я разрешаю — подключись сам и скачай нужные
данные».

Это решение владельца, и оно в силе. Но рамки сохраняются:

- **только `SELECT`**, никаких `INSERT`/`UPDATE`/`DELETE`/DDL;
- **никаких торговых эндпоинтов, админ-действий и обращений к BingX API**;
- **не выгружать таблицу `settings`** — там зашифрованные ключи BingX, PIN-хэш и
  VAPID-ключи. В скрипте выгрузки её нет, так и оставить.

У пользователя есть **проектный токен Railway** — он давал его в чате. Здесь он
намеренно не записан: это учётные данные, и в репозитории им не место. Попроси токен
или строку подключения у пользователя.

Автоматический классификатор может блокировать обращения к проду с причиной
`[Production Reads]` даже при разрешении пользователя. Если так — не обходить, а
сказать пользователю: снимается добавлением Bash-permission в настройках.

## 5. Что делать дальше: получить данные

Цель — получить папку CSV и положить её в `data/raw/`. Любым из путей.

### Путь А (основной): пользователь запускает выгрузку у себя

```bash
git fetch origin claude/dreamy-feynman-kixump
git checkout claude/dreamy-feynman-kixump
./scripts/pull-journal-data.sh
```

Нужен `psql` и строка подключения.

**ВАЖНО про строку подключения:** снаружи Railway нужен **`DATABASE_PUBLIC_URL`**.
Обычный `DATABASE_URL` указывает на `postgres.railway.internal`, который резолвится
только изнутри Railway. Скрипт это распознаёт и говорит прямо.

Если `DATABASE_PUBLIC_URL` в переменных нет: Railway -> сервис Postgres -> Settings ->
Networking -> Public Networking -> Enable.

**Пользователь уже пробовал этот путь и написал «не сработало», но причину сообщить
не успел.** Это первое, что надо у него выяснить: текст ошибки. Вероятные причины —
нет `psql`, нет публичного доступа у сервиса, ошибка подключения.

### Путь Б: веб-консоль Railway, без psql вообще

Railway -> сервис Postgres -> вкладка **Data** -> можно выполнять запросы и выгружать
результат. Подходит, если на машине нет `psql`. Таблицы, которые нужны, перечислены
в `scripts/export-journal-data.sh` — оттуда же можно взять точные `SELECT`.

### Путь В: дамп базы

```bash
pg_dump "$DATABASE_PUBLIC_URL" > bablo_snapshot.sql
```

Затем поднять копию локально и работать с ней — прод при этом неприкосновенен.

### Как данные попадают в репозиторий

`data/` добавлена в `.gitignore` намеренно: это реальная история сделок, и решение
коммитить её — за пользователем. Чтобы передать:

```bash
git add -f data/raw && git commit -m "Выгрузка журнала" && git push
```

## 6. Что делать, когда данные появятся

```bash
pip3 install pandas numpy scipy scikit-learn

python3 analysis/profile_data.py   data/raw   # ПЕРВЫМ: сколько данных и какого качества
python3 analysis/discriminate.py   data/raw
python3 analysis/counterfactual.py data/raw
```

`profile_data.py` запускать первым: он показывает объём, покрытие свечами и
снапшотами индикаторов. Если свечей нет — контрфактический анализ работать не будет.

### Чего реально ожидать

Зависит от числа сделок, и это надо сказать пользователю честно:

- **Контрфактический анализ** (`counterfactual.py`) даст рабочие ответы почти при
  любом объёме — он детерминированный, это прогон по реальным свечам.
- **Поиск зависимостей** (`discriminate.py`) при выборке в сотню сделок, скорее всего,
  скажет «различимы только крупные эффекты». Это **не провал инструмента**, а
  информация: доказано на синтетике, что настоящий эффект силой ~±1R при n=120
  неотличим от шума, а при n=600 находится.

Не поддаваться соблазну «смягчить критерии, чтобы что-то нашлось». Смысл всей
конструкции — отличать находку от узора в шуме.

## 7. Решения в коде, которые важно не сломать

Каждое из них поймано на практике и стоило ошибки. Если будешь менять код — не
откатывай это.

**Геометрия входа восстанавливается, а не берётся из `sl_price`.** В `trades` лежит
ТЕКУЩИЙ стоп, подвинутый трейлинг-лестницей и ночным правилом 1/1. Исходный риск —
`risk_usd / quantity` (порт `server/src/journal/logic.ts#entryRiskDistance`).

**Исход берётся по экономике, а не по типу ордера.** Порт
`server/src/history/outcome.ts#resolveTradeOutcome`: стоп, закрывшийся в плюс, — это
тейк. Цифры обязаны совпадать со статистикой в приложении.

**Абсолютные ценовые уровни исключены из признаков.** В первом прогоне топ находок
возглавили `ema200`, `ema50`, `dayVwap` — но разделяют они не тейки и стопы, а BTC,
ETH и SOL. Остались только нормированные величины: проценты, отношения, доли ATR.

**Признаки разворачиваются по направлению сделки (суффикс `_dir`).** Перекупленность
губительна для лонга и безразлична для шорта; в общей куче эффекты лонгов и шортов
взаимно гасятся. Без разворота заложенный в синтетику эффект **не находился вообще**.

**Поправка на множественные сравнения обязательна.** При ~95 признаках порог p<0.05
даёт около 5 «значимых» находок на чистом шуме. Везде FDR; в скане порогов —
перестановочный порог по максимуму статистики (выходит около |z|=3.8 вместо
наивного 1.96).

**Неопределённый исход реплея — не победа.** Если свечей не хватило, сделка помечается
`undetermined` и в экспектацию не идёт. Считать такие сделки тейками — главный способ
нарисовать себе грааль.

**Контрфактическое правило применяется ко ВСЕМ сделкам, а не только к убыточным.**
Расширив стоп, легко «спасти» половину стопов и незаметно испортить тейки.

**База сравнения — тот же движок.** Вариант сравнивается не с фактической историей, а
с прогоном исходной геометрии через тот же реплей, иначе в «улучшение» попадёт
собственная погрешность движка. Насколько ему верить, показывает калибровка (раздел 0
отчёта `counterfactual.py`): доля реальных исходов, которые он воспроизводит.

**Ловушка с датами.** `astype("int64")` на datetime возвращает число в **собственном
разрешении колонки** (pandas парсит ISO в микросекунды, а не наносекунды). Из-за этого
сравнения времени ломались молча. Для перевода в миллисекунды использовать
`load.to_epoch_ms()`, закрыто тестом на все четыре разрешения.

## 8. Горизонт свечей (ограничивает контрфактический анализ)

`server/src/journal/marketData.ts` собирает окна вокруг сделки:

| Таймфрейм | До входа | После закрытия |
|---|---|---|
| 5м | 1 день | 6 часов |
| 15м | 3 дня | 1 день |
| 1ч | 12 дней | 3 дня |

Реплей идёт каскадом 5м -> 15м -> 1ч: сначала самый точный, при неопределённости —
следующий, с большим горизонтом. Проверить «стоп был бы шире» можно лишь в пределах
этих окон; за ними исход честно помечается `undetermined`.
