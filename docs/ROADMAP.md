# Roadmap — этапы разработки

Каждый этап — самостоятельный, логически завершённый инкремент. Реализуем строго по порядку,
следующий этап начинаем после приёмки предыдущего.

## Этап 0 — Скелет проекта и деплой
**Цель:** пустое, но работающее приложение на Railway, устанавливаемое как PWA на iPhone.

- Монорепо (client + server, npm workspaces), TypeScript everywhere.
- Fastify-сервер: healthcheck, раздача статики клиента.
- React + Vite + Tailwind, PWA-манифест + service worker, нижняя таб-навигация (3 пустых экрана).
- PostgreSQL на Railway, Drizzle + первая миграция.
- Деплой на Railway, проверка установки PWA на iPhone.

**AC:** приложение открывается по URL Railway; ставится на домашний экран iPhone и запускается standalone; healthcheck зелёный.

## Этап 1 — Админка: ключи и активы
**Цель:** подключение к BingX и управление активами.

- Вход по PIN (сессии).
- Экран админки: ввод BingX API key/secret (шифрование в БД), проверка соединения (запрос баланса).
- CRUD активов: символ + плечо (сид: TIA 20x, TAO 25x, VIRTUAL 25x, WLD 20x).
- BingX REST-клиент (подпись запросов, баланс, информация о контрактах).

**AC:** ключи сохраняются и валидируются; на дашборде виден реальный баланс; активы редактируются и отражаются в табах.

## Этап 2 — Открытие сделки (ядро)
**Цель:** полный двухшаговый флоу открытия сделки.

- Дашборд: табы активов, текущая цена (пока REST-запрос по действию, realtime — этап 4).
- Шаг 1: объём (кол-во монет) + цена SL → Купить/Продать → market-ордер
  (изолированная маржа, one-way, плечо актива) + немедленный SL-ордер.
- Шаг 2: TP вручную или пресетом R/R (от фактической цены входа) → выставление на бирже.
- Карточка активной сделки: все параметры + цена ликвидации.
- Блокировка «уже есть активная сделка».

**AC:** сделка открывается на реальном аккаунте BingX за ≤4 действия; SL/TP выставлены на бирже; карточка показывает корректные данные; вторую сделку открыть нельзя.

## Этап 3 — Риск-движок
**Цель:** принудительное соблюдение риск-плана.

- Таблица лестницы уровней (сид из RISK_ENGINE.md), редактируемая в админке.
- Проверка объёма при открытии (по подтверждённой интерпретации) + подсветка поля.
- Дневные счётчики R, все 4 блокировки (включая часовой кулдаун после каждой сделки),
  пояснение причины + таймер разблокировки в UI.
- Учёт результата закрытой сделки в прогрессе уровня.
- Юнит-тесты на чистую логику риск-движка.

**AC:** сделка сверх лимита не отправляется; все 4 блокировки срабатывают и снимаются вовремя; при блокировке видны причина и таймер; прогресс уровня меняется по результатам сделок; тесты зелёные.

## Этап 4 — Realtime без поллинга
**Цель:** живые данные без циклических запросов.

- WS-коннектор BingX: market stream (цены активов) + account stream (listenKey, продление, реконнект).
- Детект закрытия по SL/TP через ACCOUNT_UPDATE + событийная REST-сверка.
- SSE-канал к клиенту, живое обновление цены, баланса, карточки сделки, блокировок.

**AC:** цена и PnL обновляются без перезагрузки; закрытие по стопу на бирже отражается в приложении и запускает риск-логику; в логах нет циклических REST-опросов.

## Этап 5 — История и статистика
**Цель:** экран истории с инсайтами.

- Список сделок со всеми полями (дата, актив, направление, длительность, R/R, результат %).
- Инсайт «время дня прибыльных сделок».
- Пагинация/фильтры по минимуму.

**AC:** все закрытые сделки видны с корректными данными; инсайт считается верно.

## Этап 6 — Геймификация: дерево роста
**Цель:** визуальная мотивация следовать плану.

- Экран/шит с деревом уровней: пройденные, текущий с прогрессом, будущие.
- Компактный индикатор уровня на дашборде.
- Анимация перехода уровня.

**AC:** дерево отражает реальный прогресс risk_state; переход уровня анимируется; дашборд не перегружен.

## Этап 7 — Расширенный трекинг и сигналы
**Цель:** данные для глубокого анализа во вкладке «Статистика».

- Трекер активной сделки: MFE, пересечение безубытка (по тикам WS).
- Определение и фиксация базовых сигналов (набор согласуем отдельно).
- Вкладка «Статистика» в истории с этими данными.

**AC:** по каждой новой сделке зафиксированы MFE и флаг безубытка; данные видны в статистике.

MFE и безубыток реализованы полностью (трекер по WS-ценам, без поллинга) — см.
[RISK_ENGINE.md](./RISK_ENGINE.md#расширенный-трекинг-сделки-для-статистики) за точной
формулировкой. Конкретный набор «сигналов» (пересечения/структура) в исходном плане
явно оставлен открытым («согласуем отдельно») — в БД под них зарезервировано поле
`signals` (jsonb), логика их вычисления добавится, когда набор будет определён.

## Этап 8 — Редизайн Истории: инсайты и месячная статистика
**Цель:** сделать вкладки «Сделки» и «Статистика» полезными для анализа, а не просто журналом.

- Карточки сделок: реализованный результат в USDT вместо %; причина закрытия показана
  только для SL/TP, для «на бирже»/«вручную» подпись не выводится вовсе (15.07.2026 —
  сначала объединили обе метки в «Вручную», затем убрали слово совсем как неинформативное).
- Карточка-подсказка на вкладке «Сделки»: почасовые инсайты (прибыльные/стоп-часы, часы без
  сделок — склеены в диапазоны с раскрытием по кнопке, а не список из 24 строк), самый
  прибыльный актив, типичный час достижения дневной цели +NR (`server/src/history/insights.ts`).
- Вкладка «Статистика» **репурпожена**: вместо построчного MFE/безубыток-трекинга по каждой
  сделке — карточки по месяцам (`server/src/history/monthlyStats.ts`): % к депозиту, сумма R,
  винрейт, TP/SL/безубыток, торговые дни, разбивка по пресетам R/R. Данные MFE/`beCrossed`
  продолжают собираться трекером и хранятся в БД, но сейчас не выводятся в UI — при
  необходимости для них нужно будет спроектировать отдельное место (например, разворачиваемая
  деталь на карточке сделки).
- Новая таблица `equity_snapshots`: один снимок эквити в день, лениво создаётся при загрузке
  дашборда — база для «% к депозиту».

**AC:** обе вкладки истории отражают новый дизайн; тесты на инсайты и месячную статистику
зелёные; для месяцев без снимка эквити % корректно отсутствует (не падает и не искажается).

### Правка: % к депозиту доступен для всей истории, не только «вперёд» (15.07.2026)

Изначально % к депозиту работал только «вперёд» от появления `equity_snapshots` (14.07.2026):
для месяцев без снимка ровно на начало месяца % не считался. Пользователь захотел, чтобы
уже существующие сделки тоже участвовали в статистике — переписали расчёт базы на
восстановление «в обратную сторону» от последнего известного снимка (anchor): текущий
баланс минус реализованный PnL всех сделок, закрытых с начала нужного месяца. Так % теперь
доступен для всей истории сделок, а не только для месяцев после появления снимков.

Единственный риск такого восстановления — пополнения/выводы средств между целевым месяцем
и текущим моментом искажали бы результат на их сумму. Добавлена таблица
`equity_adjustments` (date, amountUsd, note) и раздел в админке
(`client/src/screens/admin/EquityAdjustmentsSection.tsx`,
`GET/POST/DELETE /api/admin/equity-adjustments`) — пользователь вручную регистрирует
пополнения/выводы, они учитываются в восстановлении базы наравне с PnL сделок.

### Правка: правило «2 стопа за день» и фикс бага классификации закрытий (16.07.2026)

Добавлено новое дневное ограничение: 2 и более сделки за день, закрытые по стопу (в любом
порядке, независимо от суммы R), блокируют торговлю до сброса дня — как и лимиты −2R/+3R,
но считается отдельно (`daily_stats.sl_count`, `risk/limits.ts#evaluateDailyLimitBlocks`,
`risk/service.ts#recordTradeClose`). Мотивация: даже если убыток компенсирован прибылью по
сумме R, два подряд/за день промаха по стопу — сигнал потери дисциплины входа.

При разборе жалобы пользователя на неверные подсчёты в подсказках («Сделки») и месячной
статистике нашли реальный баг, а не просто проблему форматирования: `getOrderStatus` в
`bingx/client.ts` не распаковывал ответ BingX `{ data: { order: {...} } }` (как и `placeOrder`,
BingX оборачивает результат в `order`), поэтому `status` всегда был `undefined`. Из-за этого
резервная REST-сверка `reconcilePositionFlat` никогда не могла определить FILLED-статус SL/TP
и ВСЕГДА помечала закрытие как `"external"`, даже когда сделка реально закрылась по стопу или
тейку. Баг исправлен + добавлен тест (`bingx/client.test.ts`).

**Уточнение (тот же день):** после первого фикса пользователь нажал «Пересверить закрытые
сделки» и получил «7 сделок не требуют пересмотра» — ни одна не починилась. Оказалось, есть
и второй, более глубокий баг: точечный лукап ордера по `orderId` (`GET .../trade/order`) у
BingX ненадёжен именно для STOP_MARKET/TAKE_PROFIT_MARKET (условных/trigger) ордеров — после
срабатывания он может отдавать «order not exist» по исходному orderId (задокументированная
особенность BingX, не наша ошибка парсинга). Из-за этого даже с первым фиксом реконсиляция
не находила FILLED-статус для реально сработавших SL/TP. Решение: `findFilledSlOrTp`
(`realtime/reconcile.ts`) теперь сначала сканирует историю ордеров символа через новый
`getOrderHistory` (`GET .../trade/allOrders`, окно от открытия сделки до сейчас) и ищет нужный
`orderId` в списке — это надёжнее точечного лукапа для условных ордеров; `getOrderStatus`
остался запасным путём. Заодно исправлен маленький сопутствующий баг: в ветке "не удалось
определить, что сработало" (`external`) отменялась только SL-сторона по умолчанию — теперь
отменяются оба ордера (sl и tp), чтобы не оставить висящий reduceOnly-ордер на будущее.
Покрыто тестами (`realtime/reconcile.test.ts`, `bingx/client.test.ts`). Восстановительный
путь для уже закрытых «external»-сделок не изменился: `POST /admin/reclassify-trades`
(`trades/reclassify.ts`, кнопка «Пересверить закрытые сделки» в
`client/src/screens/admin/BingxKeysSection.tsx`) — использует ту же обновлённую логику поиска.

Также уточнена логика инсайтов на вкладке «Сделки» (`history/insights.ts`):
- «Самые прибыльные часы» — раньше час считался прибыльным, если хоть одна сделка в нём была
  прибыльной (`resultR > 0`), и показывалось число прибыльных сделок. Переопределено на долю
  сделок, закрытых именно по тейку: час попадает в список, если `tpCount / total ≥ 50%`
  (с 22.07.2026 — включительно ровно 50%; раньше было строго `> 50%`);
  формат подсказки — `9ч — 4/5 TP` (открыто 5, из них 4 по тейку).
- «% прибыльности активов» — список всех активов с долей TP (`VIRTUAL - 2/5 TP (40%)`),
  вместо одного «самого прибыльного» по сумме $ (решение от 22.07.2026).
- «Чаще убыточные сделки по: …» — топ активов по числу стопов (зеркало стоп-часов).
- Формат часа в подсказках сокращён до `9ч` (было `9-10ч`) — компактнее.
- «Самый прибыльный актив» — раньше показывалось только число сделок по тейку без знаменателя
  (`(0 сделок по тейку)`, что выглядело как ошибка на малой выборке). Потом — доля от всех
  сделок лучшего по $ актива; с 22.07.2026 заменено на полный список активов (см. выше).
- Формат диапазона часов ранее был `9-10ч` (ещё раньше `09:00–10:00`) — компактнее и
  единообразно для обеих строк («прибыльные часы» и «часто идут в стоп»).

В карточке месяца на вкладке «Статистика» убрано дублирование слова после числа торговых дней
(«Торговых дней: 2 торговых дней» → «Торговых дней: 2») — лейбл уже описывает значение.

**Третий, окончательный баг (тот же день):** после второго фикса `getOrderHistory` всё равно
не находила совпадений — «Пересверить закрытые сделки» снова возвращала 0 исправлений. Вместо
дальнейших догадок по документации в `/admin/reclassify-trades` и `findFilledSlOrTp` добавили
подробную диагностику (сколько ордеров в истории, найден ли сохранённый orderId, статус,
текст ошибки API, полный дамп сырых объектов ордеров) и попросили пользователя прогнать кнопку
ещё раз. По реальным данным от BingX нашли причину: **исходный условный (STOP_MARKET/
TAKE_PROFIT_MARKET) ордер никогда не становится `FILLED`** — при срабатывании он остаётся
`CANCELLED` навсегда, а BingX создаёт отдельный новый market-ордер с ДРУГИМ `orderId`, у
которого поле `triggerOrderId` указывает на orderId исходного условного ордера. Пример из
диагностики: наш сохранённый `sl = 2077751560515465200` навсегда `CANCELLED` в истории, но
там же есть ордер `orderId: 2077762124407599000, status: FILLED, triggerOrderId:
2077751560515465200` — это и есть реальное исполнение SL. Это подтвердилось на всех 7
проверенных сделках без исключений.

Фикс: `findFilledSlOrTp`/`findFilledSlOrTpDebug` (`realtime/reconcile.ts`) теперь ищут в
истории FILLED-ордер, у которого `triggerOrderId` (или, на всякий случай, сам `orderId`)
совпадает с сохранённым `orderId` SL/TP — а не просто ордер с тем же `orderId`. Добавлено
поле `triggerOrderId` в тип `BingXOrderStatus` (`bingx/client.ts`) и тест на этот сценарий
(`realtime/reconcile.test.ts`). Диагностический вывод (`historyOrders`, статусы,
ошибки API) оставлен в `/admin/reclassify-trades` и в админке — полезен, если через
BingX API снова обнаружится похожая неочевидность.

### Правка: два новых правила «день удался» (18.07.2026)

К дневным лимитам −2R / +3R / 2 стопа добавлены два правила фиксации успешного дня
(согласовано с пользователем 18.07.2026):

1. **2 тейка за день** (`daily_stats.tp_count`) — даже два раза 1:1 (+2R суммарно)
   достаточно, чтобы остановиться до завтра.
2. **Стоп → тейк ≥ 2R** (`daily_stats.strong_recovery_after_sl`) — после просадки
   сильный откуп 1:2+ закрывает день. Порядок важен: `TP → SL` торговлю не останавливает.

Чистая логика — в `risk/limits.ts#evaluateDailyLimitBlocks`; счётчики обновляются
постфактум в `dailyStats.addTradeResultToDailyStats` при закрытии сделки.

### Правка: ручная блокировка часов 9 и 10 с проверкой винрейта (22.09.2026)

По запросу пользователя часы **9:00 и 10:00** (таймзона риск-плана, UTC+3 = МСК) закрыты
для открытия сделок принудительно — не расчётом правила убыточных часов, а решением.
Гипотеза «без утра винрейт выше» проверяется РАЗ: по итогам первого завершённого месяца
начиная с октября 2026 его винрейт сравнивается с сентябрём 2026. Выше — часы закрыты
бессрочно; равен или ниже — открываются.

Почему понадобился отдельный механизм, а не просто две строки в `hour_blocks`:
`syncHourBlocks` вызывается на каждом закрытии сделки и на старте сервера, и гистерезис
«эталон ×1.5» снял бы такую блокировку на первой же закрытой сделке — эти часы как раз
недавно по нему и открылись. Поэтому у блокировки появилось происхождение
(`hour_blocks.source`) и свои параметры снятия (`review_baseline_month`,
`review_from_month`, `reviewed_at`), а авто-правило ручные блокировки не трогает вовсе.

Решения, принятые при проработке:

- **Винрейт — тот, что на карточке месяца** (`MonthlyStat.winRate`, доля сделок с
  результатом > 0), и считается тем же `computeMonthlyStats`. Это НЕ доля тейков, которой
  оперируют гистограмма часов и проверка гипотезы от 18.09.2026 — две разные цифры.
  Выбран экранный вариант: иначе на экране 62%, а движок решил по 48%.
- **Проверка разовая** (решение пользователя): подтвердилась — час закрыт навсегда, и
  сравнение больше не повторяется.
- **Месяц без сделок переносит проверку**, а не проваливает её: ноль сделок дал бы винрейт
  0% и снял блокировку без оснований. База сравнения при переносе не смещается.
- **«Не смогли проверить» никогда не значит «открыть»**: нет базы — час остаётся закрытым.
- **Тумблер «Блокировать убыточные часы» гасит и ручные блокировки** — один выключатель на
  весь механизм закрытых часов.
- Проверка гоняется и в `evaluateLosingHourBlock`, а не только на закрытии сделки и старте
  сервера: иначе после смены месяца час остался бы закрытым до первой закрытой сделки, а
  закрыть её как раз и мешает этот час.
- В админке появился блок «Закрыты вручную» со ссылкой «открыть»
  (`DELETE /api/admin/hour-blocks/:hour`). Без него при подтверждённой гипотезе
  единственным выходом был бы тумблер, выключающий заодно и авто-правило.

Сентябрь как база слегка смазан: блокировка поставлена 22.09, то есть ~3 недели месяца
отторгованы С этими часами. Чистого «дореформенного» месяца уже не существует, пользователь
об этом предупреждён и выбрал сентябрь.

Миграция `0018_manual_hour_blocks.sql` учитывает, что час мог быть УЖЕ закрыт авто-правилом:
завести вторую активную строку на тот же час нельзя (частичный уникальный индекс), поэтому
существующая блокировка переводится в ручную (`UPDATE`), и только открытые часы заводятся
новой строкой (`INSERT`). Наивный `INSERT ... WHERE NOT EXISTS` молча оставил бы такой час
авто-блокировкой, и гистерезис открыл бы его — запрос пользователя не выполнился бы.
Оба сценария прогнаны на одноразовой локальной базе.

Чистая логика — `server/src/risk/hourBlockReview.ts` (под тестами), состояние и обвязка —
`risk/hourBlocksService.ts`, данные — миграция `0018_manual_hour_blocks.sql`.

## Этап 9 — Журнал разбора сделок: отдельная PWA «Bablo.Дневник» (23.09.2026)

**Цель:** замкнуть петлю обратной связи по качеству исполнения — дневник пост-анализа
закрытых сделок с категориями, обязательными чек-листами и таблицей анализа, полностью
изолированный от торгового контура. Полное описание — docs/PROJECT.md («Журнал разбора
сделок»), архитектура — docs/ARCHITECTURE.md.

- Отдельная PWA на том же origin: `journal.html` (вторая точка входа Vite), статический
  `journal.webmanifest` (имя «Bablo.Дневник», scope `/journal`), своя иконка, общий SW с
  двумя NavigationRoute. Вход только прямым URL `/journal` — ссылок между терминалом и
  журналом нет ни в одну сторону. PIN-сессия общая.
- Сервер: модуль `server/src/journal/` (schema/logic/repository/routes/view), таблицы
  `journal_categories / journal_checklist_items / journal_entries / journal_answers`
  (миграция `0019_journal.sql`), API `/api/journal/*`. Из основного — только чтение
  `trades` и общий `history/outcome.ts` (исход и R те же, что в Истории).
- Клиент: `client/src/journal/` — экраны «Разбор» (лента с фильтрами), деталь сделки
  («картина сделки» + «Для анализа»: впервые показаны MFE и «возврат к безубытку»,
  которые трекер собирает с Этапа 7), «Анализ» (таблица с агрегатами «В плюсе/В минусе»),
  конструктор.

Решения, принятые при проработке (все — 23.09.2026):

- **Два таба, конструктор внутри «Анализа»** — выбор пользователя из трёх UX-вариантов
  (три таба / два таба / одна лента с шитами).
- **Одна категория на сделку** (UNIQUE trade_id): один разбор по одному чек-листу, смена
  категории переписывает разбор целиком — ответы на другой чек-лист не переносятся.
- **Три типа ответа** («Да/Нет», 0–10, текст) — расширяемый enum, новый тип добавляется
  без ломки данных (значения в типизированных колонках, не jsonb — агрегаты простым кодом).
- **Обязательность чек-листа — серверная** (`validateAnswers`): клиентский disabled только
  дублирует, как и все проверки в проекте.
- **«Неразобранные» не хранятся**: закрытая сделка без строки `journal_entries` — очередь
  разбора наполняется сама, без фоновых задач и рассинхрона.
- **Архив вместо удаления** для категорий с разборами и пунктов с ответами; тип пункта
  после создания не меняется. Физически удаляется только пустое. В таблице анализа
  архивные пункты с ответами остаются колонками с пометкой.
- **ON DELETE CASCADE от trades**: «Очистить данные для нового аккаунта» честно уносит
  разборы; категории/чек-листы остаются — это настройки, а не данные аккаунта.
- **Палитра через CSS-переменные**: токены Tailwind переведены на
  `rgb(var(--x-rgb) / <alpha-value>)`; `:root` — прежний айвори (терминал не изменился ни
  на пиксель, проверено сборкой), `theme-journal` — своя гамма журнала. Добавлены
  смысловые токены `positive/negative/muted`. Первая версия гаммы была серой iOS
  (systemGroupedBackground #F2F2F7) — пользователь счёл её унылой, и в тот же день она
  заменена на «Небо» (#F5F9FF, голубые линии, сине-серые подписи, systemBlue-акцент);
  вариант выбран из двух живых превью (второй — лаванда с systemIndigo). Урок: серые
  «системные» нейтрали iOS на большом фоне выглядят казённо, светлый цветной фон
  приятнее.
- **Грабля workbox, чтобы не повторить**: NavigationRoute матчит `pathname + search`,
  паттерн `/^\/journal(\/|$)/` НЕ ловил `/journal?x=1` — такой URL получал терминал
  (найдено на локальном смоуке со стабом API). Правильный паттерн —
  `/^\/journal([/?]|$)/`; серверный fallback по той же причине сравнивает путь без query.
- Иконка рисуется полигонами (не stroke-path): PNG собирается ImageMagick-ом, его
  MSVG-рендер stroke у path не рисует.
- **Правка читаемости детали и настроек** (23.09.2026, жалоба на «неровный текст»):
  пары «метка — значение» переведены на общий `DetailRow` — двухколоночная сетка с
  фиксированной колонкой меток (значения на одной вертикали, выравнивание влево),
  `tabular-nums` для цен, тонкие разделители строк вместо голых отступов; шкала 0–10 в
  опроснике — ровная сетка 6 колонок вместо flex-wrap (ряды 7+4 выглядели рвано);
  у иконок-кнопок конструктора расширена зона нажатия (иконка 14px, тап ~34px).
  Урок: значения и многострочные пояснения НЕ выравнивать по правому краю — рваное
  начало строк ломает чтение; правый край — только для однострочных чисел-итогов.
- **Звёзды 0–5 и порядок пунктов drag-and-drop** (23.09.2026). Четвёртый тип ответа
  `stars_0_5` подтвердил заложенную расширяемость: значение легло в существующую
  `value_int`, агрегат — то же среднее, что у шкалы, миграция не понадобилась. Ноль
  звёзд достижим повторным тапом по выбранной звезде (обязательный опросник требует
  различать «не отвечено» и «0» — рядом со звёздами цифра «n/5»). Порядок пунктов —
  `PUT /api/journal/categories/:id/items-order` (перестановка строго всех активных
  пунктов, `validateItemsReorder` под тестами) + drag-and-drop в конструкторе на
  pointer events без библиотек: захват за ручку-грип с `touch-action: none`, локальная
  перестановка на каждом пересечении границы строки, сохранение на отпускании, при
  ошибке refresh возвращает серверный порядок.
- **Рабочая зона графика и рыночные данные в БД** (23.09.2026). Свечи BingX — публичный
  klines без ключей (`getKlines` рядом с getLatestPrice); кэш в `journal_candles`
  вечный: период закрытой сделки не меняется, график не зависит от глубины истории
  биржи, окно на сделку — 15м −3д/+1д и 1ч −12д/+3д (факт сбора — `journal_candle_syncs`,
  candles_fetched=0 честно фиксирует «истории уже нет»). Сбор автоматический: хук в
  finalizeTradeClose (fire-and-forget, как push), бэкфилл на старте (последовательно с
  паузой 300мс) и ленивый добор в GET графика. Тем же проходом считается снапшот
  индикаторов на момент входа (последняя ЗАКРЫТАЯ свеча до входа — текущая ещё
  формировалась) по обоим ТФ + MAE/MFE по свечам — `journal_trade_metrics` с
  METRICS_VERSION для будущих пересчётов; в UI не выводится (решение пользователя).
  График — свой canvas (~600 строк) без библиотек: пан, зум колесом, pinch двумя
  пальцами, переключение 15м/1ч, уровни входа/SL/TP, маркеры входа-выхода, рисование
  и стирание трендовых линий; линии хранятся на сервере в координатах (время, цена) —
  переживают смену ТФ и зум (проверено на стабе). Прочее: содержимое области — под
  ctx.clip (линии не выезжают на оси); hit-test выбора линии — расстояние точка-отрезок
  в пикселях экрана с радиусом 8px; в TS narrowing не доходит до function declaration
  из-за хойстинга — canvas в обработчике берётся из event.currentTarget.

Проверено: `npm test` (307, включая новые тесты `journal/logic.test.ts`), `npm run
typecheck`, `npm run build`; UI — на локальной сборке со стабом API (полный флоу: разбор
сделки с чек-листом, смена фильтров, таблица с агрегатами, конструктор). Боевой сервер и
BingX не затрагивались; вживую проверить после деплоя: установка второй PWA на iPhone
(имя/иконка), пуш-подписка живёт в терминале как раньше, `/journal` с прода.
