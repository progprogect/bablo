# Bablo — личный торговый терминал для BingX

## Что это

Минималистичное приложение-прослойка над BingX (USDT-M Perpetual Futures) для одного трейдера.
Главная цель — сделать процесс открытия сделки максимально быстрым и **автоматически принудить к соблюдению риск-плана**: приложение само блокирует сделки, нарушающие план, и защищает от тильта.

- Деплой: Railway (один сервис + PostgreSQL).
- Клиент: PWA, устанавливается на iPhone через «Добавить на экран Домой» (без подписи, нужен только manifest).
- Пользователь: один (личное использование), вход по PIN.

## Ценность

| Проблема | Решение в Bablo |
|---|---|
| Терминал биржи перегружен, открытие сделки — много кликов | Один экран, 4 актива табами, 2 поля, 2 кнопки |
| Нарушение риск-плана «на эмоциях» | Риск-движок проверяет каждую сделку до отправки на биржу |
| Тильт после убытков / эйфория после прибыли | Автоблокировки кнопки открытия по дневным лимитам |
| Нет мотивации следовать плану долго | Геймификация: визуальное дерево роста уровней риска |
| Нет данных для анализа своих сделок | Автотрекинг каждой сделки (MFE, безубыток, сигналы) |

## Экраны (всего 3 + навигация нижними табами)

### 1. Главный экран (дашборд) — единственный «рабочий» экран

- Сумма депозита (баланс фьючерсного аккаунта).
- Индикатор текущего уровня риска и прогресса (компактный, ведёт на дерево роста).
- Табы активов: **TIA · TAO · VIRTUAL · WLD** (набор редактируется в админке).
- Форма открытия сделки (см. флоу ниже).
- Карточка активной сделки (если есть): актив, лонг/шорт, цена входа, SL, TP,
  сумма риска, R/R, плечо, цена ликвидации, текущий PnL.
- Если действует блокировка — кнопки открытия заблокированы, показана причина и таймер до разблокировки.

### 2. История (2 вкладки внутри экрана)

**Вкладка «Сделки»:**
- Карточка-подсказка над списком:
  - «Прибыльные часы» — часы открытия, в которые **не меньше половины** (≥ 50%) открытых
    в этот час сделок дошли до тейка (не просто `resultR > 0` у отдельной сделки — час считается
    прибыльным по доле тейков среди сделок, открытых в нём). Формат: `9ч — 4/5 TP` (открыто
    5 сделок, 4 из них дошли до тейка). Порядок — по «силе» часа: число тейков ↓, при
    равенстве — доля тейков ↓ (`1/1` выше `1/2`), и только полностью равноценные часы идут
    по времени ↑. Показаны все подходящие часы (первые 6 сразу, остальные — кнопкой
    «и ещё N»): час, видимый в истории как тейк, не должен молча пропадать из подсказки.
    Раньше был топ-3 по числу тейков — час с одним тейком вытеснялся более «объёмными»
    часами, а порядок равных решал номер часа неявно (правка от 13.08.2026).
  - «% прибыльности» — по каждому активу с закрытыми сделками: доля дошедших до тейка
    среди всех его сделок, формат `VIRTUAL - 2/5 TP (40%)`. Сортировка по hitRate ↓.
  - Статистика по пресетам R/R — по каждому пресету отдельной строкой, только `tpCount/totalTrades`
    и %; список раскрывается по кнопке, если пресетов много. Разбор причины промаха (стоп, средний R)
    убран — при нескольких похожих пресетах эти фразы дублировались и захламляли карточку.
  - «Чаще убыточные сделки в: …» — часы, в которые **больше половины** (> 50%) открытых
    сделок закрылись по стопу. Формат, порядок и раскрытие списка — как у прибыльных часов
    (число стопов ↓, доля ↓, час ↑; первые 6 + «и ещё N»).
    Ровно 50% (например `1/2`) — час не входит.
  - «Чаще убыточные сделки по: …» — активы с наибольшим числом закрытий по стопу
    (формат `TIA (2), VIRTUAL (1)`, топ-2).
  - типичный час достижения дневной цели +NR.
  - «Среднее время отработки сделки R/R 1/3: 2ч - 7ч» — min–max длительности (часы) сделок
    с пресетом 1/3, закрытых по тейку; чтобы понимать, сколько обычно ждать тейк, а не
    сидеть в графике. Строка последняя; скрывается, если таких тейков ещё нет.
- Карточки сделок: актив, лонг/шорт, дата/время открытия, продолжительность, R/R, реализованный
  результат в USDT (со знаком, зелёным/красным). Причина закрытия показана по фактическому
  исходу (тейк / стоп / безубыток), см. ниже; для ручного закрытия и обнаруженного постфактум
  на бирже подписи нет.
- **R в карточке** (правка от 15.08.2026): вид строки прежний — `R/R 1/1.1`, — но значение
  **фактическое**, а не плановое, и округлено **до десятых**. Плановый пресет в карточке
  не показывается: он ничего не говорит о результате. Знак не выводится — он виден по
  подписи исхода и цвету суммы; при нулевом R (безубыток) соотношение скрыто целиком,
  «R/R 1/0» ничего не сообщает.
  Факт приходит с сервера полем `statsResultR` (тот же R, что идёт во всю статистику, с
  учётом ручного столбца R из админки), поэтому карточка и отчёты разойтись не могут.
  Раньше показывался только план, и по истории нельзя было понять, что сделка реально
  дала; при TP, выставленном вручную, план ещё и считался от ТЕКУЩЕГО стопа — стоп мог
  быть подтянут ночным правилом, знаменатель схлопывался, и сделка на ~2R показывалась
  как «R/R 1/19.65».
- **Округление R — только при выводе**, одним хелпером `client/src/lib/format.ts`
  (`roundR` / `formatRatioR` / `formatSignedR`). Сервер отдаёт R с полной точностью
  намеренно: на нём считаются % к депозиту и восстановление эквити прошлых месяцев,
  там округление накапливалось бы в расчётах. Тем же хелпером округляются суммы R в
  месячной карточке — иначе История и Статистика легко разъезжаются по правилам.
- В админке («R в статистике») у сделки показывается время **открытия** — то же, что в
  Истории. Раньше там было время закрытия, и одна сделка выглядела на двух экранах
  как две разные.

**Вкладка «Статистика»:** карточка на каждый месяц (сначала новые) —
% результата к депозиту, сумма R, всего сделок, разбивка TP/SL/безубыток, винрейт, число
торговых дней, разбивка по пресетам R/R (подписаны множителем — «1R, 1.5R, 2R…»,
нулевые пресеты тоже показаны) и рядом с ней — суммарный R отдельно по прибыльным и
по убыточным сделкам за месяц («+R / −R»). Сетка R строится **по факту, а не по плану**: столбец
определяется фактически достигнутым R (тейк на +2.09R при плане 1/3 идёт в 2R, а не в 3R);
плановый пресет остаётся только запасным вариантом, если достигнутый R не близок ни к
одному уровню сетки. Учитывается и **исполненная частичная фиксация** (сделка с partial 2R
→ столбец 2R, в том числе если остаток закрылся по БУ). Partial не сработала / выбило
по стопу — в сетку не идёт (это SL). Ночной TP 1/1, если сделка закрылась по этому
тейку — **везде считается тейком**: в разбивке TP/SL месяца, в столбце 1R, в инсайтах
(прибыльные часы, % прибыльности, пресеты) и в дневных лимитах — ровно как обычный TP,
потому что закрытие по нему это `closeReason = "tp"`.

**Исход сделки считается по экономике, а не по типу сработавшего ордера**
(`server/src/history/outcome.ts` — единый источник правды для месячной статистики,
инсайтов, дневных лимитов и подписи в истории):

- закрытие по стопу, который стоял **на стороне прибыли** (ночное подтягивание SL на 1/1,
  правило «ход ≤ 2R» после partial), и с положительным R — это **тейк**: прибыль
  зафиксирована нашим же решением, план защиты не срабатывал. В сетке R такая сделка идёт
  в столбец по **уровню стопа** (SL на 1/1 → столбец 1R), а не по плановому `rrPreset`;
- результат в пределах **±0.05R** — безубыток (в истории подпись «Безубыток»);
- стоп ниже входа (для лонга) или закрытие в минус — обычный **SL**, даже если стоп был
  уведён в прибыль, но проскальзывание дало убыток.

Исключение — метрики «дошла ли цена до плана»: статистика по пресетам R/R и «среднее время
отработки 1/3» по-прежнему считают тейком только настоящий `closeReason = "tp"`.
Зафиксированный на 1/1 стоп до пресета 1/3 не дошёл, но и «ценой промаха» не является —
в строку пресета он не идёт ни как тейк, ни как стоп (правка от 15.08.2026).

Чтобы правило работало не только «на бумаге», причина закрытия определяется по факту
у биржи во всех путях закрытия, а не только по WS-событию: при ручном закрытии, когда
позиции на бирже уже нет, и при старте сервера с активной сделкой без позиции сервер
ищет реально исполнившийся SL/TP-ордер (`realtime/filledOrder.ts`). Раньше эти два
пути безусловно писали `external`, и сделка, закрытая ночным тейком во время
деплоя/обрыва стрима, не попадала ни в тейки статистики, ни в дневные лимиты
(правка от 13.08.2026). Для уже закрытых таких сделок в админке есть «Пересверить
закрытые сделки» (чинит причину по данным BingX, пока они там есть — до 7 дней) и
ручная «Классификация сделок». В админке («R в статистике») можно вручную задать
столбец R для любой закрытой сделки или «не учитывать».

Заданный там R — **источник правды для всех R-метрик** этой сделки, а не только для
столбца сетки: месячная сумма R, «+R / −R», винрейт и инсайты считают её ровно как
выбранный R (знак от исхода: тейк → +2R, стоп → −2R). До 15.08.2026 правка меняла
только столбец, из-за чего сделка могла числиться в админке как 2R, а в сумме месяца
давать 20R.

Что оверрайд R НЕ меняет осознанно: **деньги** (USDT в Истории и % к депозиту) и
**риск-движок** (дневные лимиты −2R/+3R, лестница уровней). Деньги реальны — эквити
прошлых месяцев восстанавливается вычитанием фактического PnL из текущего баланса, и
подменённый R сломал бы сходимость с балансом на бирже; обычно ошибка как раз в
записанном риске, а `resultR × riskUsd` при этом верен. Риск-движок остаётся на факте,
чтобы правка отчёта не могла случайно снять блокировку дня. На список сделок в Истории
(поле `rrPreset`) правка тоже не влияет.

Там же для **любой** закрытой сделки (включая уже классифицированные биржей и старые)
задаётся **исход**: «Тейк», «Стоп», «Б/У» или «авто». Оверрайд (`trades.stats_outcome`)
главнее всех авто-правил и действует сразу во всех местах: месячная разбивка TP/SL/БУ,
сетка R, подсказки на «Сделках», дневные лимиты риск-движка (включая правило #9 по
активу) и подпись в карточке Истории. Причина закрытия с биржи (`closeReason`) при этом
НЕ затирается — оверрайд лежит отдельным слоем, поэтому «Пересчитать» и сверки с BingX
продолжают видеть реальный факт. В строке видно и авто-значение, и текущее
(`исход Стоп → Тейк (вручную)`). Дневные лимиты за текущий день пересобираются сразу
после правки (правка от 15.08.2026).
Кнопка «График роста депозита» открывает полноэкранный шит с
кривой линией по снимкам эквити (**осознанное исключение** из принципа «без графиков»
ниже, подтверждено пользователем 14.07.2026) — растёт только вперёд, с момента
появления первого снимка, без восстановления прошлых точек.

% к депозиту считается не по снимку ровно на начало каждого месяца (таблица снимков
эквити молодая, для прошлых месяцев такого снимка физически нет), а восстановлением
"в обратную сторону" от последнего известного снимка: берём текущий баланс и вычитаем
из него реализованный PnL всех сделок, закрытых с начала нужного месяца, а также ручные
пополнения/выводы за тот же период (`equity_adjustments`, задаются в админке — иначе
любое пополнение исказило бы % за все месяцы до него). Так процент доступен для ВСЕЙ
истории сделок, а не только для месяцев после появления снимков.

### 3. Админка

- BingX API-ключи (хранятся зашифрованными на сервере).
- Управление активами: символ, плечо (TIA 20x, TAO 25x, VIRTUAL 25x, WLD 20x), добавление/замена.
- Кастомизация параметров риск-плана: лестница уровней, дневные лимиты, время сброса дня (по умолчанию 07:00 UTC+3).
- Пополнения/выводы средств (дата, сумма, заметка) — для корректного % к депозиту в «Статистике» (см. выше).
- «Пересверить закрытые сделки» — повторно сверяет с BingX сделки, закрытые как «внешние»
  (`closeReason = "external"`), и чинит причину закрытия (SL/TP) там, где BingX ещё хранит
  данные по ордеру. Нужна из-за бага в `getOrderStatus` до 16.07.2026 (см. ARCHITECTURE.md).
- «Классификация сделок» — список закрытий без SL/TP (`external` — на бирже мимо приложения,
  `manual` — кнопкой «Закрыть»). Админ вручную помечает «Стоп» или «Тейк»; после этого
  инсайты и дневные лимиты учитывают сделку как SL/TP (`POST /admin/trades/:id/close-reason`).
- «Очистить данные для нового аккаунта» — полный сброс истории/прогресса перед подключением
  другого BingX-аккаунта (недоступно при активной сделке).

## Флоу «Открыть сделку» (двухшаговый)

**Шаг 1 — вход в позицию (SL обязателен до входа):**
1. Выбираю актив табом.
2. Заполняю «Объём позиции» (количество монет) и «Цена SL».
3. Нажимаю **Купить** или **Продать**:
   - риск-движок считает точный риск: `|текущая цена − SL| × количество`;
   - если риск выходит за допуск от 1R текущего уровня (L1 ±20%, L2+ ±10% —
     больше ИЛИ меньше) — поля подсвечиваются красным, сделка не отправляется;
   - если ок — рыночный ордер (изолированная маржа, one-way, плечо из настроек актива)
     и **сразу** выставляется SL-ордер.

**Шаг 2 — тейк-профит:**
4. Заполняю «Цена TP» вручную, либо выбираю пресет R/R: `1/1 · 1/1.5 · 1/2 · 1/3 · 1/4 · 1/5 · 1/6 · 1/7 · 1/8 · 1/9 · 1/10`
   (TP рассчитывается от фактической цены входа и SL). При пресете **1/5 и выше**
   (или ручном TP с таким же R/R) обязательно указываю цену частичной фиксации 70% —
   пресетами `1/1 · 1/2 · 1/3` или вручную, **не дальше R/R 1/3** от входа.
5. Нажимаю **Сохранить** — на бирже выставляется TP, показывается карточка активной сделки.

**После исполнения частичной фиксации** (правило «ход ≤ 2R», 26.07.2026): сервер отменяет
исходный SL и ставит новый `STOP_MARKET` на **остаток** объёма:
- partial ≈ **1/3** → SL на **R/R 1/1** (от фиксации до стопа = 2R);
- partial ≈ **1/2** → SL на **цену входа** (от фиксации до стопа = 2R).
Partial на 1/1 правило не включает. Идемпотентно; при рестарте/деплое дотягивается для уже
открытой сделки с `partialTpFilledAt`, если SL ещё не на стороне прибыли.

**Ночное правило 1/1** (26.07.2026, развилка по цене — 15.08.2026): если сделка открыта
утром/днём/вечером (не в окне **01:00–07:00 МСК**) и после **01:00** всё ещё активна,
сервер смотрит текущую цену и делает одно из двух:

- **цена ещё не дошла до 1/1** — отменяет текущий TP (и незаполненный partial) и ставит
  один `TAKE_PROFIT_MARKET` на **R/R 1/1 × 100% остатка**, чтобы не пересиживать ночь;
- **цена уже прошла 1/1, но до планового TP не дошла** — тейк **не трогает** (план
  продолжает работать), а подтягивает **SL на уровень 1/1**: хуже +1R сделка закончиться
  уже не может. Ставить в этом случае TP на 1/1 нельзя — он оказался бы позади рынка и
  сработал бы сразу, закрыв сделку в 01:00 вместо того, чтобы дать ей доработать.

Уровень 1/1 считается от **исходного** риска (`riskUsd / quantity`), поэтому уже
подтянутый стоп расчёт не искажает. Если SL уже стоит на 1/1 или дальше (например, после
partial 1/3) — правило не нужно и ничего не делает. Если цену получить не удалось —
работает первая ветка (перенос TP), как до 15.08.2026.

Сделки, открытые уже после 01:00, не трогает. Идемпотентно (`nightTpAppliedAt`); при
деплое в ночном окне — применяется сразу; днём — одноразовый таймер до следующих 01:00
(без поллинга).

Замена условного ордера (и здесь, и в правиле «ход ≤ 2R» после partial) идёт через общий
`replaceConditionalOrder`: старый ордер отменяется, новый ставится, и **если новый
выставить не удалось — прежний возвращается на место**, а его новый `orderId` пишется в
`bingxOrderIds`. Раньше при сбое биржи позиция оставалась вообще без тейка (или без
стопа), а в БД лежал id уже отменённого ордера, по которому потом не определялась и
причина закрытия. Незаполненный partial теперь гасится только после того, как новый TP
реально встал.

**PnL при проскальзывании SL** (05.08.2026): если BingX в ORDER_TRADE_UPDATE присылает
`rp=0`, а цена закрытия (`ap`) даёт заметный убыток/прибыль — считаем результат по цене,
а не по нулевому `rp`. В админке («R в статистике») кнопка **Пересчитать** заново берёт
цену: fill SL/TP с BingX → сохранённый `closePrice` → при SL с close≈entry — `slPrice`.

## Ограничения (риск-движок)

Кнопка «Купить/Продать» блокируется, если:

| Условие | Блокировка |
|---|---|
| Закрылась любая сделка (кулдаун, независимо от результата) | на 1 час |
| За день зафиксировано −2R от депозита | до 07:00 следующего дня |
| За день зафиксировано +3R | до 07:00 следующего дня |
| За день 2 и более сделки закрыты по стопу (независимо от порядка и суммы R) | до 07:00 следующего дня |
| За день 2 и более сделки закрыты по тейку (даже если сумма меньше +3R) | до 07:00 следующего дня |
| Был стоп, а после него тейк ≥ 2R (1:2+) | до 07:00 следующего дня |
| По активу сегодня уже был стоп (`closeReason = sl`) | повторный вход в **этот** актив до 07:00; другие активы доступны |
| Уже есть активная сделка в приложении | пока сделка не закрыта |
| На BingX открыта позиция не через приложение | пока позиция не закрыта на бирже |

При глобальной блокировке UI показывает понятное пояснение причины и таймер до разблокировки.
При блокировке по активу после стопа — плашка со списком закрытых активов и таймером до
сброса дня; форма открытия остаётся для остальных активов. Позиции, открытые вручную на
бирже (не через приложение), показываются на дашборде отдельным read-only блоком (без
SL/TP/риска — они неизвестны приложению) вместо формы открытия сделки.

Важно: блокировки действуют **только на открытие новых сделок**. Активная сделка никогда
не закрывается системой принудительно — она дорабатывает до своего SL/TP или ручного
закрытия, и лишь после этого её результат учитывается в дневных лимитах.

Детали риск-плана и лестницы уровней: см. [RISK_ENGINE.md](./RISK_ENGINE.md).
Архитектура: см. [ARCHITECTURE.md](./ARCHITECTURE.md).
Этапы разработки: см. [ROADMAP.md](./ROADMAP.md).

## Принципы продукта

1. **Минимализм**: один главный экран, остальные — только при необходимости. Никаких графиков, стаканов, лент сделок.
   Единственное осознанное исключение — график роста депозита на вкладке «Статистика»
   (простая линия по дневным снимкам эквити, без внешних библиотек), добавлено по
   явному запросу пользователя 14.07.2026.
2. **Дисциплина важнее свободы**: приложение не даёт нарушить план — это фича, а не ограничение.
3. **Скорость**: открытие сделки — не более 4 действий.
4. **Без поллинга**: realtime через WebSocket BingX и SSE к клиенту.
